# Security Notes — Pharmaceutical Regulatory Compliance Agent

**Scope of this document:** the Phase-3 demo application (`backend/main.py` + `frontend/`) and the LLM-explanation path, audited 2026-10-20 (workstream B). This is a research prototype and local demo — **not** a certified, audited, or production-hardened system. Nothing here is a security certification. Findings state only what was tested, with the evidence named.

## Threat model

- **Submitted documents are untrusted.** Anyone who can reach the API can submit arbitrary text, including text designed to attack the system (prompt injection, XSS payloads aimed at the reviewer UI).
- **Retrieved regulatory text is untrusted data.** Corpus text is treated as reference material, never as instructions.
- **The LLM is untrusted.** Its output is display text only. The compliance verdict is produced entirely by the deterministic rule engine *before* any LLM call, and LLM output is written only into the `explanation` / `suggested_fix` string fields of a violation — it cannot create, remove, re-grade, or re-label findings (proven by test, §3-F).
- **Deployment assumed by this audit:** a single user running the app locally (`uvicorn backend.main:app`, default localhost). There is **no authentication, no authorisation, no TLS, and no multi-user isolation** — do not expose this app to a network you do not fully control.
- **Out of scope:** the host OS, the user's browser, the LLM providers' own security, and the clinical/legal correctness of any finding.

## Potential risks (not confirmed exploitable; recorded, not fixed here)

- **Explanation manipulation.** The explainer prompt (`src/rag_explainer.py`) places instructions and retrieved/document text in a single user message, with the retrieved text under a labelled block ("RELEVANT REGULATORY TEXT… cite only these"). There is no system-role separation. A crafted document or corpus passage could bias the *explanation wording* shown to a reviewer. Impact is bounded: explanations cannot change the verdict, severity, or evidence (see S6 tests), and reviewers see the deterministic evidence alongside. Treat explanations as untrusted draft text, always. Hardening (system-message separation, instruction/data delimiters) belongs to the `src/` workstream.
- **Provider error strings in explanations.** `explain_violation_with_llm` embeds `str(e)` from a failed LLM call into the returned `explanation` field. Provider error messages do not normally contain API keys, but they can contain request metadata. Recommend a generic fallback message (src/ workstream).
- **No authentication / rate limiting / audit logging.** Acceptable for a single-user local demo; blocking issues for any shared deployment.
- **No request timeout on LLM calls** beyond the provider client's defaults; a slow provider can hold a request open. Local-demo impact only.
- **Dependency vulnerabilities were not audited** in this workstream (no `pip-audit` run against the full `requirements.txt`); the dependency workstream owns that check.

## Data handling

- **Never submit real patient data to this system.** It is a research prototype with regex-level PII *detection*, not a de-identification tool, and submitted text may be sent to a third-party LLM API when explanations are enabled (`COMPLIANCE_USE_LLM=1` with a Groq/OpenAI key configured). The repository contains only synthetic documents; keep it that way.
- **API keys** are read only from environment variables / a local `.env` file (`.env` is gitignored; `.env.example` in the repo contains empty placeholders only — verified 2026-10-20). Keys are never logged, never returned in API responses (regression: `test_api_key_never_appears_in_response`, sentinel-key check), and are passed only to the configured LLM provider client. The S1 traversal fix also closes the path by which a local `.env` could have been downloaded through `/static`.
- The API is stateless: submitted reports are not stored by the backend. Server stderr may contain tracebacks (which can include snippets of submitted text from exception context) — treat server logs as sensitive if real text were ever processed.

This is a personal research project, not a maintained product. If you find a security problem, open a GitHub issue describing the behaviour *without* including any real patient data, credentials, or third-party private information — or contact the repository owner privately for anything sensitive. There is no bug-bounty programme and no guaranteed response time.
